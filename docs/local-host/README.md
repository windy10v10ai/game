# 本地主机策略

> 背景：Dota 2 官方自定义游戏服务器故障，玩家在可预见的一段时间内只能用本地主机开局。本文档给出「哪些功能在本地主机直接放开、哪些必须走网站登录」的总体建议，不展开技术实现细节。

## 一句话结论

**本地主机只做「读取、限额产出、个人设置、小额会员积分消耗、自己掏钱的充值」；所有改变账号养成状态的操作（加点、洗点、觉醒）一律改到网站（Steam 登录）操作，游戏内只做跳转和刷新。**

## 1. 问题是什么

原先只有官方服务器能拿到可信的服务器密钥，后端据此相信「请求里的 steamId 就是这个玩家本人」。本地主机拿不到这把钥匙，现在临时用一个打包进地图的 API key 顶替，但地图一解包 key 就泄露，所以后端**不能**再相信本地主机发来的任何 steamId。

这意味着本地主机下每一个「改账号数据」的接口都存在两类风险：

| 风险 | 例子 |
|------|------|
| 凭空造资源 | 伪造结算报文刷勇士积分，伪造每日任务完成 |
| 冒充别人操作 | 拿别人的 steamId 给他洗点、给他乱加属性、刷举报 |

限额只能压住第一类，第二类只能靠「让玩家本人登录」解决，这就是网站方案的价值。

### 当前代码现状

客户端侧 `ApiClient` 在本地主机只放行三个路径，其余请求直接在本地返回 401，根本不会发到后端：

| 接口 | 用途 | 本地现状 |
|------|------|---------|
| `GET /game/start` | 加载玩家数据、每日任务候选 | 放行 |
| `POST /game/end/local` | 本地结算（后端限每日 2000 勇士积分） | 放行 |
| `POST /daily-task/refresh` | 刷新每日任务候选 | 放行 |
| `PUT /player/:id/property` | 勇士积分加属性点 | 拦截 |
| `DELETE /player/:id/property` | 洗点（勇士积分 / 会员积分） | 拦截 |
| `PUT /player/:id/setting` `game-preset` | 键位、预设保存 | 拦截 |
| `GET /player/:id/info` | 刷新玩家信息（会员状态） | 拦截 |
| `GET /player/ranking` | 排行榜 | 拦截 |
| `POST /player/member-points/use` | 抽奖付费刷新（会员积分） | 拦截（抽奖模块另有本地判定） |
| `PUT /player/:id/hero-awakening` `/random` | 觉醒解锁、随机觉醒 | 拦截 |
| `POST /player/conduct` | 点赞 / 举报 | 拦截 |
| `POST /alipay/order/*` | 支付宝购买会员 | 拦截 |

前端目前没有「当前是本地主机」的标记，按钮点了没反应，玩家只能靠加载页 FAQ 得知原因。

## 2. 分级原则

判断一个功能放在哪一档，依次问三个问题：

1. **被冒用会不会让别人凭空得利？** 会 → 至少加限额。
2. **会不会改变受害者的账号养成状态，且不可逆？** 会 → 走网站。不看攻击者有没有动机，只看受害者能不能挽回。
3. **是否消耗付费资源（会员积分）？** 是 → 本地只开小额限额，大额走网站。

| 档位 | 定义 | 处理方式 |
|------|------|---------|
| A 本地直接放开 | 只读、个人设置、或钱由操作者自己出 | 客户端放行，后端做基础校验、限流和审计 |
| B 本地放开但限额 | 会产生或消耗资源，但单位金额小 | 后端按 steamId 每日限额，超出直接丢弃 |
| C 仅网站 | 改变账号养成状态且不可逆 | 游戏内按钮改为「前往网站」，操作完成后回游戏刷新 |

## 3. 功能分档建议

### 总览表

| 功能 | 当前（本地主机） | 未来打算 | 本地主机是否允许 | 不允许时是否迁移到网站 |
|------|-----------------|---------|-----------------|---------------------|
| 加载玩家数据、每日任务候选 | 允许 | 不变 | 允许 | — |
| 本地结算勇士积分 | 允许，每日 2000 上限 | 暂时保持 2000，后续看情况上调 | 允许（限额） | — |
| 每日任务（领取、刷新候选、结算奖励） | 允许 | 不变 | 允许 | — |
| 会员签到 | 允许 | 不变 | 允许 | — |
| 键位、游戏预设保存 | 拦截 | 客户端放行 | **改为允许** | — |
| 玩家信息刷新（会员状态、属性） | 拦截 | 客户端放行，兼作网站操作后的同步入口 | **改为允许** | — |
| 排行榜读取 | 拦截 | 客户端放行 | **改为允许** | — |
| 购买 / 续费会员（支付宝） | 拦截 | 客户端放行，后端对下单接口做限流与异常检测 | **改为允许** | —（网站也提供购买入口，两边都能买） |
| 抽奖付费刷新（会员积分） | 拦截 | 放开，后端限每日 1000 会员积分、单笔不超过 50 | **改为允许（限额）** | — |
| 勇士积分加属性点 | 拦截 | 游戏内属性面板改为只读 + 「前往网站」 | 不允许 | 迁移到网站 |
| 洗点（勇士积分 / 会员积分） | 拦截 | 同上 | 不允许 | 迁移到网站 |
| 觉醒英雄解锁（直购 / 半价认领） | 拦截 | 游戏内按钮改为「前往网站」 | 不允许 | 迁移到网站 |
| 随机觉醒抽候选 | 拦截 | 同上，候选集在网站生成与认领 | 不允许 | 迁移到网站 |
| 点赞 / 举报 | 拦截 | 维持现状，不改 | 不允许 | 不迁移（冒用风险高，且网站无对局上下文） |
| GA4 统计上报 | 不上报（后端只对官方服务器下发配置） | 后端对本地 key 也下发配置 | **改为允许** | — |

以下按档位说明理由。

### A 档：本地直接放开

| 功能 | 理由 |
|------|------|
| 加载玩家数据、每日任务候选 | 已放行 |
| 键位、游戏预设保存 | 纯个人设置，冒用无意义 |
| 玩家信息刷新 | 只读，同时是网站操作完成后回游戏同步数据的入口 |
| 排行榜读取 | 只读 |
| 每日任务候选刷新 | 已放行，后端本身有次数限制 |
| GA4 统计上报 | 不开就没有任何统计数据。开关在后端的开局接口，对本地 key 也返回 GA4 配置即可，游戏侧不用改。接受这期间混入假数据 |
| 购买 / 续费会员（支付宝） | 钱由付款人自己出，被「冒用」等于别人替受害者充值，没有损失。真正的风险是下单接口被脚本刷，靠后端限流（按 steamId / IP 限制下单频率、未支付订单数量）和异常检测处理 |

后端对 A 档写操作的最低要求：记审计日志，按 steamId 限流。不追求绝对安全，只挡最简单的脚本乱刷。

### B 档：本地放开但限额

| 功能 | 限额 |
|------|------|
| 本地结算勇士积分 | 沿用后端每日 2000 上限，暂不调整，后续按官方恢复情况决定是否上调 |
| 每日任务奖励 | 已放行，任务奖励本身固定且每日一次，天然限额 |
| 会员签到 | 已放行，每日一次 |
| 抽奖付费刷新（会员积分） | 放开，后端按 steamId 限每日 1000 会员积分，单笔不超过 50。理由：单次金额小、是会员的核心游戏内体验，全部堵死会让会员觉得白花钱；限额后即使被冒用，损失也可控 |

### C 档：仅网站操作

| 功能 | 理由 |
|------|------|
| 勇士积分加属性点 | 被冒用会把受害者的积分加到不想要的属性上，攻击者虽无利可图，但受害者要花积分洗点才能挽回。和洗点、觉醒同属「不可逆地改变养成状态」，不单独开口子 |
| 洗点（无论用勇士积分还是会员积分） | 一次性大额消费，且被恶意触发会毁掉受害者的养成进度 |
| 觉醒英雄解锁、随机觉醒 | 账号级永久解锁，大额消费，冒用后无法回滚 |
| 点赞 / 举报 | 被冒用可刷举报陷害他人，维持当前拦截不动，不提供网站入口 |

## 4. 网站方案

在后端项目里用 Firebase 搭一个网站，Steam OpenID 登录后即可确认「操作者就是这个 steamId 本人」，然后提供 C 档所有操作。

### 网站需要提供的页面

- 属性面板：查看当前属性，加点，洗点
- 觉醒：查看已觉醒英雄，解锁、随机
- 会员：查看积分与到期时间，购买 / 续费（游戏内也能买，网站是第二入口）
- 记录：最近的积分变动、消费记录（方便玩家自查是否被冒用）

### 游戏内配合

- 加载完成后把「当前是否本地主机」发到客户端（一个 net table 字段即可），前端据此把 C 档按钮显示为「前往网站操作」，点击用 `ExternalBrowserGoToURL` 打开对应页面。属性面板在本地模式下只展示、不能点
- 各页面保留「刷新」按钮（复用现有的玩家信息刷新事件），玩家在网站操作完后回游戏手动点一下即可生效，不做即时推送。这一步放在最后实现。属性变化需要重新应用到英雄身上，现有的加点成功回调已经做了这件事，可直接复用
- 加载页 FAQ 里的本地主机条目改写，明确告诉玩家哪些能在本地做，哪些去网站做

### 后端配合

- 请求来源分三类：官方 key、本地 key、网站登录态。每个接口显式声明允许哪几类，默认拒绝本地 key
- 本地 key 随每次地图更新轮换，旧 key 立即失效，缩短泄露窗口
- 本地 key 的所有写操作记审计日志，异常量（同一 steamId 短时间大量请求、steamId 不在任何近期本地对局名单里、未支付订单堆积）自动拦截并告警

## 5. 分阶段落地

| 阶段 | 内容 | 目的 |
|------|------|------|
| 1 立即 | 客户端放行 A 档接口和抽奖付费刷新；后端加限流、审计、每日会员积分消耗上限；游戏内加本地主机标记，加点等 C 档按钮置灰，鼠标悬停提示「新的加点方式开发中」 | 先把能放的放开，让玩家知道加点为什么不能用 |
| 2 短期 | 网站 Steam 登录 + 属性 / 觉醒 / 会员页面；游戏内跳转按钮；FAQ 文案更新 | 补上加点、洗点、觉醒 |
| 3 收尾 | 游戏内「刷新」按钮同步网站操作结果 | 网站与游戏数据打通 |
| 4 视情况 | 结算上限上调；本地 key 轮换机制 | 养成节奏与安全收尾 |
| 5 官方恢复后 | 保留网站作为长期入口，本地策略继续生效 | 官方服务器再挂时不用重来一遍 |

### 阶段 1 细分

game（Workshop 地图）和 firebase（后端）是两个独立发布的东西，阶段 1 拆成两步：**后端先上，game 后上**。后端只是多放行几个接口，旧地图在本地根本不会调它们，先上没有副作用；反过来新地图先上，玩家会对着还没放行的接口撞 401。

**1a 后端（可以按接口拆成多次部署，不必一次上完）**

| 改动 | 说明 |
|------|------|
| 本地 key 放行名单 | 键位 / 预设保存、玩家信息刷新、排行榜、会员积分消耗、支付宝下单与查询 |
| 会员积分消耗限额 | 本地 key 来源按 steamId 限每日 1000、单笔 50，超出直接拒绝 |
| 支付宝下单限流 | 按 steamId / IP 限下单频率和未支付订单数 |
| 开局接口 | 对本地 key 也返回 GA4 配置 |
| 审计日志 | 本地 key 的所有写操作落日志，便于事后排查冒用 |

**1b game（一次 release）**

| 改动 | 说明 |
|------|------|
| 客户端放行名单 | 与后端名单对齐。带 steamId 的路径是动态的，现有的精确匹配要改成前缀匹配 |
| 抽奖付费刷新 | 去掉技能 / 物品抽奖里的本地主机拦截，限额交给后端 |
| 本地主机标记 | 开局后把「是否本地主机」下发到客户端，供前端判断 |
| 加点 / 洗点 / 觉醒按钮 | 本地主机下置灰，悬停提示「新的加点方式开发中」 |
| 加载页 FAQ | 改写本地主机条目，说明现在哪些能用 |
| 本地化文案 | 上面两项涉及的中英俄文案 |

game 侧这几项都很小，合成一次 release 即可，不建议再拆。若置灰 UI 拖了进度，可以先发放行部分，让玩家先把设置保存、排行榜、付费刷新用起来，UI 随下一次 release 补上。

## 6. 已定决策

- 抽奖付费刷新：每日会员积分消耗上限 1000，单笔不超过 50
- 网站操作后的同步：玩家手动点刷新，不做即时推送，最后实现
- 点赞 / 举报：维持现状拦截，不需要特意修改
- 网站上线前：本地主机下加点按钮置灰，鼠标悬停提示「新的加点方式开发中」
- GA4 统计：本地主机也上报，接受假数据风险
