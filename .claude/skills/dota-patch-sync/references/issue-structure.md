# 主 issue 与子 issue

## 结构

一个主 issue 汇总整体进度，下面挂子 issue（GitHub 的子问题）。标题统一 `Dota2 <版本>同步 …`。

主 issue 正文：

- 官方更新日志链接
- 玩家已反馈的问题与根因（如果有）
- 本地资料位置：`docs/reference/<版本>/`（说明该目录不入库）
- 子 issue 清单，按优先级

子 issue：

| 优先级 | 子 issue | 内容 |
|---|---|---|
| 1 | 紧急修复 | 冲击面判断中的「阻断」项，见 `impact-triage.md` |
| 2 | 配置格式或规则变化 | 如中立物品等级与格式，视版本而定 |
| 3 | 基础物品覆盖复核 | 本图已覆盖或克隆的物品，配方与数值是否被官方改动冲突 |
| 4 | 确认类，每个更新日志章节一个 | 综合改动、中立生物、物品、中立物品、英雄 |
| 视需要 | 地图地形 | 更新日志「地图改动」，要更新地形文件时单列 |
| 视需要 | 电脑眼位更新 | 地形更新后单列，按新地图重新规划眼位，见 `dota-map-update` |

子 issue 挂到主 issue 下，GitHub 的 `addSubIssue` 接口（GraphQL）或网页「子问题」都行。

## 项目看板

仓库看板「开发计划」（组织项目 3）按状态管理：

- 有进展的卡片放 Todo，没进展的放 Plan，做完的 Done
- issue 关闭会被自动标成 Done，重新打开的主 issue 要手动改回
- 状态字段与选项 ID 用 `gh project field-list 3 --owner windy10v10ai --format json` 取，移动用 `gh project item-edit`

## 勾选规则

- 完成的项写明由哪个 PR 完成，勾上
- 不做的项划掉并注明原因，例如「不需要，更新地形文件时会自动变化」「不做，等玩家反馈再说」，也勾上，避免看起来没处理
- 清单与进度一起回填，别等全部做完再写
- 子 issue 完成条件：没有空框。有空框但需要等待的，保持打开并在行内写明在等什么

## 正文写法

- 先用一句话说清这件事影响玩家什么，编号只作链接
- 不要把 issue 写成模板空壳：确认类 issue 刚建时可以只有「对照章节、标出影响、拆工作项」几条，但开始做时要立刻改成真实的勾选清单

## 创建与更新

- 创建用 `gh issue create`，正文写文件再 `--body-file`
- 更新 issue 正文前先读当前正文，用文件处理后 `gh issue edit --body-file`，别整段重写丢掉已勾项
- 中文正文不用全角分号，发出前扫一遍
