# 把审查结论回复到 PR

用户明确说要发才做，评论先给用户看草稿。不提交 APPROVE / REQUEST_CHANGES。

- **方案完整版挂到 issue**：做成自包含 HTML，按 `.claude/references/doc-writing.md`「issue artifact」挂成名为「设计」的附件。给 `Artifact` 工具写的源文件没有 `<!doctype html>`、`<head>`、`<body>` 外壳（发布时自动加），挂到 GitHub 前补上。没有关联 issue、或只有一两处小问题时省掉附件，内容直接写进评论
- **PR 评论**：`gh pr comment` 发一条综述，写调整项列表、「设计」附件链接、本地验证结果，细节留在附件里。外部贡献者的 PR 开头加一句对贡献的肯定。要定位到代码行的问题用 inline 评论
- **claude.ai 的 artifact 默认只有用户能打开**：贡献者要看的内容挂 issue 的 HTML 附件，claude.ai 链接只在用户说已公开时才写进评论
- **由谁来改没定时只写改成什么**：用户没说让贡献者改还是自己改时，评论和页面都写「调整为 X」，不写「请作者改」「退回」
- **贡献者看得到的页面用中性措辞**：只写改动本身的现状、问题、调整方向，不写贡献者的用户名、对贡献流程的评价（如「没等同意就动手」）、本机环境。审查报告是写给用户的内部结论，用户要公开它时先按这条改一遍，并同步成已定的方案
- 按严重度排列，小问题点到即可，只有架构分歧（「审什么」代码第 2 条）才用较强语气
