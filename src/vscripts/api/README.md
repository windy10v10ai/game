# 客户端 HTTP 代发（Client HTTP Relay）

游廊里开的对局服务端发不出 HTTP，改由玩家客户端代发。本文写这套通道的约束与决定，做法以代码为准。
进度与阶段划分见 [issue #2435](https://github.com/windy10v10ai/game/issues/2435)。

## 为什么需要

Dota 2 不再给自定义游戏提供专用服务器，每一局都是玩家自己的机器当主机。
能不能发 HTTP 取决于**启动方式**，与单人多人无关：

| 启动方式 | 能发 HTTP | 别人能连进来 |
| --- | --- | --- |
| 游廊创建 | 否 | 能 |
| 控制台 `dota_launch_custom_game` / Dota Tools | 能 | 不能 |
| 将来自建专用服务器 | 能 | 能 |

线上玩家全是游廊启动，所以**代发是线上唯一能用的通道**，不是兜底；本地主机判定线上恒为真。
降级不猜启动方式，只在运行时看拿不拿得到请求对象。

## 传输

服务端挑一名已就绪的真人玩家，让他的客户端用隐藏网页控件加载网址，响应写在页面标题里带回。
由此带来的硬限制是后面一切规约的根源：

- **只能 GET，带不了请求头**：认证和写入的请求体都只能进 query
- **响应标题上限 4096**：超限显式报错、不静默截断，截断后的 JSON 解析失败很难查
- **请求网址上限 7427，卡在 API 前面的 CDN**，不在引擎。请求头也占这份预算，所以只能在客户端量、不能拿 curl 推。
  超限的表现是超时而不是报错，怀疑长度问题先看客户端打的 `urlLength=`。新接路由按 7000 排预算，给浏览器内核升级留余量
- **走浏览器内核**：会认 HTTP 响应头（见「中国大陆线路」），也会缓存，每条网址带随机参数破缓存

几条传输层的决定：

- **排队与请求各自计时**：游廊局客户端加载慢于 10 秒很正常，共用一个超时会让请求死在队列里。排队上限对齐客户端脚本自己的就绪重试窗口，它不再举手后再等也没用
- **代发失败的玩家拉黑，让调用方已有的重试落到别人身上**；没选在传输层另造重试循环，因为两层相乘次数和日志都不可读。全员失败过就清空重来，候选通常只有三四人
- **换人救不了区域性故障**：同一房间的玩家网络状况相关，连不上的地区要靠专门的线路
- **传输层不认识业务**：按玩家拆分、并行、合并由各业务的 Proxy 类实现，注册在原路由路径上。处理器从原请求参数里自取所需，不给请求参数加代理专用字段
- **重试只在 TS 一层**：客户端脚本只报一次失败，不加重试

## 标题预算

- **按路由裁剪代发响应，不动直连**：4096 是通道的限制，不是资源的性质。代发路由可以只回原路由的子集或换字段集，名字表达的是取哪条原路由的数据
- **随天数、随投入增长的字段不进开局包**：开局包是最热的路径，冷数据挂在上面迟早把标题撑爆。这类数据改成用到时再拉
- **不能用直连结果推断代发能不能用**：直连没有长度限制、不认响应头。验证代发要用 Tools 里强制走代理的调试开关单独跑
- 后端超限会记 `[Proxy] title too long` 日志，发现超限不必反推响应字节

## 写入型代理路由

网页控件只能发 GET，原路由是 POST / PUT / DELETE 的，代理侧全是「有副作用的 GET」。

- **只接原路由已经放行本地主机的写入**：游戏的 API key 打包在地图里、随时可能被解包。代理路由直接调 service、绕得过原路由那道门，但**不绕**——花积分的属性加点与重置、觉醒解锁与随机只认网页登录态，要接得先在后端单独决定放不放行
- **原路由对本地来源的限制必须同样生效**：限额与冷却是本地主机唯一的防线。限制写在原路由 controller 里的，先下沉到 service，两条路径调同一个方法
- **命名一律加方法后缀**：`/proxy/` + 原路径去掉路径参数拍平 + `-` + 方法小写，GET 不加；路径参数改走 query。
  一律加而不是撞车才加，是为了能从原路由机械地推出名字（`PUT` 与 `DELETE /player/:id/property` 确实会撞）
- **请求体 base64url 进 query，后端解码后走原路由的 DTO 与校验**：base64url 不需要百分号编码，膨胀比 JSON 百分号编码小；没换定长 CSV、msgpack 等更紧凑的格式，省下的字符换不回后端两套解析
- **数值先取整再进请求体**：引擎返回的属性是长小数，界面只显示整数位，取整后上报的和显示的才是同一个数
- **不做后端去重，靠调用方不重试**：代发客户端自己不会重发，重复只可能来自 game 侧重试。累加型写入只发一次，覆盖型保持默认重试；本地结算例外，后端冷却会挡住已记上的那次，所以照常重试。只有网络失败、429 与 5xx 才重试，其余 4xx 原样重发结果不变。**新增调用点先去后端确认是累加还是覆盖，不按路由名猜**

## 结算按玩家拆

- **按真人玩家拆成自包含请求，不切片**：API 保持无状态，不按对局去重
- **每条带全场真人数**：拆开后单条报文看不出人数，后端限额要用
- **失败的玩家结算就丢了**：结算是累加写入，重复结算比丢失更糟
- **接受的断供**：对局维度的 GA4 事件与 bot 行统计不走代发。限额记录里的来源 IP 会是代发玩家的，一局所有人相同
- **base64url 自己实现、按字节、不用位运算**：两边都没有现成的；LuaJIT 的位运算库在 jest 里没有，用算术两边行为才一致

## 中国大陆线路目前不可用

腾讯云函数的默认域名给每一个响应强制加 `Content-Disposition: attachment`，平台层注入、业务代码覆盖不了。
浏览器内核认这个头，页面不渲染、标题永远不会设置，还会在游戏里弹出下载对话框。
所以转交代发时直接跳过这条线路；命令行启动的局走裸 HTTP 客户端，不看这个头，照常可用。

**新接一个代发地址前先 `curl -D -` 看响应头。**

后续方向是换线路：绑已备案的自定义域名（要等备案），或买境外 VPS 自己反代（不需要备案、响应头自己说了算，推荐）。
腾讯云函数冷启动返回 502 的问题一并处理。

## 不做

- `GET /player/ranking`：加载排行榜的方法没有调用方
- GA4 埋点与 cloudflare 取时间：不走统一的 API 客户端，代发对局接受丢失
- 签名：主机本来就不可信，防线是限额不是签名
- 只认网页登录态的写入，理由见「写入型代理路由」
