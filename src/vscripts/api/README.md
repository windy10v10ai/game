# 客户端 HTTP 代发（Client HTTP Relay）

游廊里开的对局服务端发不出 HTTP，改由玩家客户端代发。

本文档只写**目的、设计、关键信息与决策**，不复述代码已经表达的东西。
进度与步骤见 [issue #2435](https://github.com/windy10v10ai/game/issues/2435)。

> **实现落地后要回来更新本文档**：待定方案改成已定、废弃的决策删掉、新踩的坑补上。

## 为什么需要

Dota 2 已经不给自定义游戏提供专用服务器，线上每一局都是玩家自己的机器当主机。
能不能发 HTTP 的分界是**启动方式**，**跟单人还是多人无关**：

| 启动方式 | 能发 HTTP | 别人能连进来 | 结算实际走哪条 |
| --- | --- | --- | --- |
| 游廊创建（单人多人一样） | 否 | 能 | 发不出去 |
| 控制台 `dota_launch_custom_game` | 能 | 不能 | `/game/end/local` |
| Dota Tools | 能 | 不能 | `/game/end/local` |
| 将来自建专用服务器 | 能 | 能 | `/game/end` |

线上玩家全是游廊启动，所以**代发是线上唯一能用的通道**，不是边缘情况的兜底。
同理，本地主机判定线上恒为真，`/game/end` 这类非 local 路由目前零流量，是为将来自建服务器预留的。

降级判定不猜启动方式，只在运行时看拿不拿得到请求对象。

## 传输设计

服务端挑一名已就绪的真人玩家，让他的客户端用隐藏的网页控件加载网址，响应写在页面标题里回传。

由此带来的硬限制，是后面一切规约的根源：

- **只能 GET，带不了请求头**。认证只能塞进 query，写入型路由的请求体也只能塞进 query
- **标题有长度上限**。超限要显式报错，不做静默截断——截断后的 JSON 解析失败很难查
- **走的是浏览器内核，会认 HTTP 响应头**。见下面「中国大陆线路」
- **浏览器内核会缓存**。每条网址都要带随机参数破缓存

### 排队与请求预算分开计时

排队等客户端举手的时间**不占用**请求自己的超时预算。

原本两者共用同一个 10 秒。实测某轮客户端 44 秒才就绪，全部请求死在队列里一次都没派发出去；
游廊 10 人局里客户端加载慢于 10 秒完全正常。

排队上限取 60 秒是对齐客户端脚本自己的就绪重试窗口——它等不到就不会再举手，再等也没用。

### 代发人失败后拉黑

代发失败就把这个玩家排除，调用方**已有的**重试自然落到下一个人。
后端返回的业务错误不拉黑——那说明网络是通的，换谁都一样。

两个决策：

- **不在传输层另造重试循环**。传输层换 3 个人、业务层再整体重发 3 次，最坏 9 次请求，
  日志里也分不清哪次是谁。拉黑的价值不是省一次超时，而是让已有的那个重试变得有意义
- **全员都失败过就清空名单重来**。候选通常只有三四人，一次抖动就永久排除会很快无人可用。
  清空即自愈，不需要计时器或恢复逻辑；三四个人配三次重试，一轮正好把人走一遍

**换人不能替代给连不上的地区准备线路**：同一房间的玩家网络状况是相关的，不是独立的，
中国大陆的房间通常全员都在墙内。换人只救个体故障，区域性问题要靠专门的线路。

### 传输层不认识业务

传输层只负责「把一个网址发出去、把标题拿回来」。按玩家拆分、并行发送、结果合并，
由各业务自己的 Proxy 类实现，注册到原路由路径上。

处理器拿得到整个请求参数对象，需要的 query 与 body 自己从里面取，
**不要给请求参数加代理专用字段**。

### 重试只在 TS 一层

客户端脚本没有任何重试，只有超时后报一次失败。新增功能不要在客户端脚本里加重试——
两层重试相乘会让次数和日志都不可读。

## 写入型代理路由的规约

网页控件只能发 GET，所以原路由是 POST / PUT / DELETE 的，代理侧全是「有副作用的 GET」。

### 命名：非 GET 一律加方法后缀

`/proxy/` + 原路径去掉路径参数拍平 + `-` + 方法小写。GET 不加后缀。
例：`POST /game/end/local` → `/proxy/game-end-local-post`，`PUT /player/:id/property` → `/proxy/player-property-put`。

**为什么一律加而不是只在撞车时加**：只在撞车时加，就没法从原路由直接推出代理路由名，
得先查有没有兄弟路由。而 `PUT` 和 `DELETE /player/:id/property` 确实会撞成同一个名字。
一律加是机械的；名字里带着方法也在持续提醒这条路由会改数据。

### 请求体：base64url 进 query

base64url 是网址安全字符集，不需要百分号编码，膨胀 1.33 倍；原始 JSON 全是括号引号冒号，
百分号编码要 1.5 倍。API 侧解出来后走原有的校验，**DTO 与校验逻辑和原路由共用，不另写一套**。

不换更紧凑的格式（定长 CSV、msgpack 等）：省下的字符换不回后端两套解析与校验的代价，
而且长度上限实测余量充足。

### 幂等：不做后端去重，靠调用方不重试

代发只是客户端加载一次网址，自己不会重发；重复执行只可能来自 game 侧的重试。
所以不引入幂等键、去重表这类后端机制，改为在调用点把尝试次数设成 1。

后端实际行为查过一遍，**累加型**（`POST /game/end` 累加积分战绩、
`DELETE /player/:id/property` 每次扣积分、`POST /alipay/order/create` 每次开新订单、
`POST /player/member-points/use` 纯扣费）已全部设成只发一次；
**覆盖型**（属性、觉醒、setting、game-preset）后端本身幂等，保持默认重试。

**新增调用点时先去后端确认是累加还是覆盖，不要按路由名猜。**

## 中国大陆线路目前不可用

腾讯云函数的默认域名（`*.tencentscf.com`）给**每一个**响应无条件加
`Content-Disposition: attachment`。代发靠的是浏览器内核，它认这个头：不渲染页面 →
标题永远不会被设置 → 必然超时；同时下载流程会在游戏里弹出文件选择对话框。

排查证据：

- curl 对比两条线路同一接口：主 API 域名无此头，腾讯云有
- 换 `text/html`、`application/json`、`text/plain` 三种响应，全都带
- 打一个不经上游、完全由函数自己生成的 404，照样带 → 平台层注入，与业务代码无关
- 在 server 项目里显式返回 `Content-Disposition: inline` 尝试覆盖，无效，被强制覆盖

**为什么以前没暴露**：服务端直连用的是裸 HTTP 客户端，根本不看这些头。这个头八成一直都在，
阶段 2 才第一次换上会认它的客户端。

> 教训：**不能用直连结果推断代发能不能用**。新接一个代发地址前先 `curl -D -` 看响应头。

处置是在转交代发的入口直接跳过这条线路。代发永远选直连——这本来就是阶段 2 之前的现状。
命令行启动的对局走裸 HTTP 客户端，不经浏览器内核，这条线路在那里照常可用。

### 后续方向

绑已备案的自定义域名（要等备案）、换腾讯云其他产品（默认域名大概率同样限制，待验证）、
**买一台境外 VPS 自己反代**（不需要备案、响应头自己说了算，推荐）。单独立项，不挡阶段 3。

另有一个未处理问题：腾讯云函数冷启动会返回 502。换线路方案后一并处理。

## 阶段 3：结算的拆分设计

方针：**不切片**，按玩家拆成自包含请求（每条 base64url 后约 984 字符），API 保持无状态。

### game 侧只新增一个 Proxy 类

注册到 `/game/end/local`，与 game-start 的那个平级。传输层、请求参数结构、结算数据的
构造入口都不用改。

**目标是 local 那条路由**：线上恒为本地主机，结算发送入口永远选 `/game/end/local`。
`/game/end` 目前零流量，本次一行都不动。

**去 bot 行放在这个新类里**，另外两个位置都不行：

- 放在结算数据的构造函数里 → GA4 的技能选择、每日任务两个 tracker 还要读 bot 行
- 放在发送入口 → 那一层不知道这局会不会走代发，直连的局会被误伤

顺带去掉 `playerId` 字段，后端 DTO 没声明它，进了 query 就是白占字符。

**每条报文都带 `playerCount`（全场真人数）**：拆成单玩家后，单条报文里再也看不出全场人数，
后端限额要用它。字段在结算数据的构造函数里统一写入，直连和代发两条路径都必带。

**base64url 编码自己实现**（`utils/base64url.ts`）：两个仓库都没有现成的，TSTL/Lua 也没内置。
按字节算，因为 Lua 字符串本来就是字节序列，序列化出来的 UTF-8 不用再转码；
不用位运算，LuaJIT 的 `bit` 库在 jest 里没有，用算术两边行为才一致。

**失败的玩家结算就丢了**：不加重试、不加幂等键。结算是累加写入，重复结算比丢失更糟。
只要有一个玩家成功，整体回调就报成功，日志里按玩家打印失败原因。

### API 侧只拆统计那块，结算原样复用

结算部分（限额检查、积分战绩、每日任务）本来就是逐玩家的，喂一份单玩家报文就能用，
**一行都不用改**。

**限额与冷却必须走这条既有路径，不能绕。** 现在已经没有可信来源了，每一局的主机都是玩家
自己的机器，限额是唯一的防线，代理路由绕过它等于开一个刷分后门。

真正要拆的是统计那个方法，它现在把三样东西捆在一起，而代发路径只要最后一样：

| 做的事 | 作用域 | 代发路径要吗 |
| --- | --- | --- |
| GA4 全场对局事件 | 对局级 | 不要 |
| GA4 bot 行事件 | 对局级 | 不要 |
| 逐玩家生涯统计累加 | 玩家级 | 要 |

拆成两个方法，原有路由挨个调、行为不变；代理路由只调后一个，且结算通过了才调。

**不需要按 `matchId` 做幂等**：代发路径既然不写对局级记录，就没有任何东西会被 N 条请求
重复写，每条只碰自己那个玩家。

### 请求体是第一条带 body 的代理路由

前三条代理路由的参数都是平铺 query，这条要先 base64url 解码再还原成 DTO，
解出来之后交给原路由同一套校验。解码这步是新增的公共工具。

### 整场拒绝退化成逐人拒绝，不另写逻辑

原本一份报文里只要有一个玩家可疑就整场拒绝，那是为了实现方便，不是安全要求。
按玩家拆之后每条报文只含一个玩家，**整场拒绝天然就等于逐人拒绝**，所以限额与冷却
这套逻辑一行都不用改，把现有方法喂一份单玩家报文即可。

### 接受的断供

只限走客户端代发的对局；命令行启动的局走原路由，统计照常。

| 丢的 | 影响 |
| --- | --- |
| GA4 全场对局事件 | 对局维度统计断供 |
| bot 行统计 | 按玩家拆后去重键全撞在一起，不换去重键、不为 bot 多发请求 |

另有一项不算断供但语义变了：限额记录里的来源 IP 会变成代发那位玩家的，一局里所有人
记的是同一个 IP。该字段目前只写不读、没有自动封禁，但日后拿它查异常时要知道这回事。

行为分不在此列——本地主机结算本来就不计算行为分，不是拆分造成的。

## 阶段 3.5：每日任务历史移出开局包

开局包里的 `dailyTasks[].history` 会把标题撑过上限，代发对局约一半玩家因此拿不到任何开局数据。

### 排查证据

判据是响应字节：错误页长度恰好等于 `requestId 长度 + 244`，成功响应则是 `标题长度 + 201`。
据此从 Cloud Logging 反推一整天的 `/proxy/game-start`：

| | |
| --- | --- |
| 请求数 / 其中超限 | 448 / 290（64.7%） |
| 去重玩家 | 152 人，72 人每次都失败，80 人从未失败，**0 人时好时坏** |

「0 人时好时坏」说明失败按玩家确定，是体积问题而非网络抖动。

撑爆的不是玩家档案：两组玩家的 `players[0]` 长度分布完全重叠（全量 151 人 min 666 / p50 1260 / max 1948）。
是历史——存储里一条只有 `taskId` 与 `star`，下发时展开成完整候选对象，通用任务 114 字符、
英雄任务约 150，一天最多三条，上限三十天。实测标题总长：三天 4039、四天 4512、三十天 17088。
**攒够三到五天就永久失败。**

### 为什么是从根部移除，不是只在代发裁剪

直连不受标题长度限制，所以问题只在代发暴露，但**两条路都在白背这十几 KB**，而直连才是流量大头。
历史只在个人资料的历史子页显示，是挂在最热路径上的冷数据。

压缩与截断都试算过，都不够：压成存储形态后三十天仍有 5062 字符，自己就超上限，
而且客户端没有任务定义表，展开要先把整张表塞进地图；截断到三天，中位玩家也已经 4247。

### 刷新是硬依赖，必须同批做

`POST /daily-task/refresh` 的响应与开局下发的是同一个快照对象，同样带历史，
**历史不出 DTO，这条路由就代发不了**。

反过来它也是阶段 4 那九条写入里最适合打头的一条：每轮刷新额度上限为一，
重复调用会撞上额度判定原样返回，是唯一天然幂等的写入，拿它把写入代发的链路先跑通最稳。

改成懒加载后，刷新的成功回调要连同已拉回的历史一起保住，否则翻过历史再点刷新会把它抹掉。

### 两条新路由

按上面的命名规约，读走 `/proxy/daily-task-history`，写走 `/proxy/daily-task-refresh-post`，
请求体照样 base64url 进 query 复用原 DTO 校验。

历史按天分页，游标是天号。**一页五天**：实测五天 2676 字符、七天 3759，
这条路由只装历史，五天能留三成余量。游标从第一版就留在接口上，客户端先只拉第一页。

## 不做

- `GET /player/ranking`：加载排行榜的方法全仓库没有调用方，是死代码
- GA4 埋点与 cloudflare 取时间：不走统一的 API 客户端，代发对局接受丢失
- 分片：按玩家拆之后不需要，API 保持无状态
- 签名：沿用现有 API key，主机本来就不可信，防线是限额不是签名
